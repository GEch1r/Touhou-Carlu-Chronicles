# 开发文档

本文档用于统一 Touhou Carlu Chronicles 的开发协作方式。后续由 AI 生成的项目文档，除非另有明确说明，统一存放在 `docs/` 目录下。

## 1. 代码格式规范

### 通用原则

- 使用 UTF-8 编码保存文本文件。
- 文件末尾保留一个换行符。
- 使用清晰、描述性的命名，避免无意义的缩写。
- 保持单一职责：一个脚本、函数或配置文件尽量只处理一类问题。
- 修改现有文件时，优先保持原有格式和风格，避免无关的批量格式化。
- 注释应说明“为什么这样做”；显而易见的代码不重复添加注释。

### 脚本与配置

- KubeJS 和其他脚本按功能拆分，文件名使用小写字母和短横线或项目已有的命名风格。
- 配置项保持稳定的缩进和分组；不要随意重排无关配置。
- 事件注册、配方、战利品和其他内容按用途分段，并使用简短注释标识区块。
- 提交前检查脚本语法，确认没有调试输出、临时路径或本地专用配置。

### Markdown 文档

- 使用 ATX 标题（`#`、`##`、`###`）。
- 标题层级按顺序递进，不跳级使用标题。
- 命令、文件名、路径、变量和配置项使用反引号包裹。
- 较长内容优先使用列表或表格表达，示例应尽量保持可复制运行。
- 文档使用中文为主；专有名词、模组名和命令保留其官方写法。

## 2. Commit 规范

Commit message 使用 Conventional Commits 风格：

```text
<type>(<scope>): <简短描述>
```

常用 `type`：

- `feat`：新增功能或内容
- `fix`：修复问题
- `refactor`：重构，行为基本不变
- `config`：调整配置、模组设置或默认配置
- `docs`：新增或修改文档
- `build`：修改 Packwiz、构建或发布相关文件
- `chore`：其他维护性变更

约定：

- 描述使用祈使语气，简明说明变更结果，不以句号结尾。
- 一次 Commit 尽量只包含一个逻辑变更。
- 不要提交个人 IDE 配置、临时文件、日志或密钥。
- 影响较大的变更应在正文说明背景、主要改动和验证方式。
- 破坏性变更在类型后标注 `!`，例如 `feat!: 调整任务数据格式`，并在正文说明迁移方法。

示例：

```text
feat(kubejs): 添加东方主题战利品表
fix(config): 修正默认生物生成规则
docs: 补充本地开发环境说明
```

## 3. 结构化开发知识记录

开发过程中形成的决策、约束和排查结论，应记录为可检索、可维护的 Markdown 文档，并放入 `docs/` 目录。推荐按以下结构组织：

```text
docs/
├─ DEVELOPMENT.md       # 协作与开发规范
├─ architecture.md      # 系统结构和模块关系
├─ decisions/           # 重要技术决策（ADR）
├─ guides/              # 操作指南和流程
├─ troubleshooting/     # 问题排查与解决方案
└─ changelog/           # 面向版本的变更记录
```

记录新知识时：

1. 先判断内容属于规范、架构、决策、指南、排错还是变更记录。
2. 在对应文档中补充，避免重复创建内容相近的页面。
3. 每条记录说明背景、结论、影响范围和验证方式。
4. 涉及版本、模组或配置时，明确写出适用版本和文件路径。
5. 技术决策发生变化时，不删除旧结论；补充新的决策及变更原因。

推荐的决策记录模板：

```markdown
# 决策：标题

- 日期：YYYY-MM-DD
- 状态：提议 / 已接受 / 已废弃
- 适用版本：

## 背景

## 决策

## 影响

## 验证方式
```

文档变更应使用 `docs` 类型的 Commit，并在文档中保持链接、路径和版本号准确。
